# 战双卡牌联机项目协作规则

## 项目目标

指导用户将现有战双卡牌模拟器改造成前后端分离的联机卡牌游戏，覆盖 Java 后端实际工作中常见的数据库、业务设计、接口、权限、缓存、实时通信、测试和部署问题。

## 协作方式

- 以教学为主：先说明本阶段要解决的问题、关键后端概念和操作方式，再由用户亲自实施。
- 教学过程中默认不直接给出可整段复制的完整实现代码，也不提前揭晓最终答案。先给目标、设计思路、关键 API、伪代码或局部骨架，让用户自行编码。
- 用户遇到问题时采用渐进式提示：先指出问题范围和检查方向，再根据用户的代码、报错或追问逐步增加提示；只有用户明确要求查看完整答案或要求代为修改时，才提供完整实现。
- 布置编码任务后，可通过理解题、运行结果、日志或局部代码检查用户是否真正掌握，再进入下一步；不要把“讲课”变成复制粘贴教程。
- 每次首次引入新的 Java 语法、关键字、类型、集合、注解、设计模式或 Spring/MyBatis 概念时，不要默认用户已掌握。应先结合当前代码解释“它是什么、解决什么问题、代码如何拆读、为什么此处使用”，并给出完成当前任务所需的最小用法，再让用户动手。
- 如果一个编码任务依赖尚未讲过的新概念，应先暂停任务补齐该概念；不要只给出陌生 API 名称后让用户自行摸索，以免用户因缺少基础词汇而无法开始。
- 讲解新的 Java、Spring 或 MyBatis 概念时，优先使用用户熟悉的 Vue 2、Vue 3、TypeScript 或前端工程概念建立直觉，再补充 Java 中的准确术语，并明确指出类比不完全成立的边界。例如用组件实例属性类比 Java 实例字段、用 TypeScript 接口类比 Java 接口、用 `const` 引用类比 `final` 引用；不要一开始只堆叠陌生后端术语。
- 不要未经请求直接替用户修改三个实际工程。用户明确要求代改时才动手。
- 用户有六年前端工作经验。不要重复讲解 Vue、TypeScript、目录复制、API 文件等基础内容，除非用户明确追问或错误证据指向这些部分。
- 后端新概念应解释清楚，但保持工程化和高效率；可以一次给出一组相互关联的操作，不必拆成过细步骤。
- 根据实际代码、日志、数据库结果判断，不凭记忆假设项目状态。
- 每完成一个可运行闭环，更新 `PROJECT_STATUS.md`。

## 教学闭环的前置审查与验收冻结

- 每个新的规则或业务编码闭环开始前，Codex 必须先完整检查该闭环依赖的规则知识库、实际卡牌原文、现有前后端代码和既定实施计划，确认基础模型能够承载本次实现后，才能向用户布置编码任务。
- 布置任务时必须一次性给出本闭环完整且可执行的验收清单，至少覆盖：合法流程、非法操作、操作发起者权限、重复提交、失败是否产生部分状态修改、区域与数量上限、动态卡牌效果的扩展接缝、败北或对局结束后的流程阻断，以及本次明确暂不实现的边界。
- 验收清单在用户开始编码后视为本闭环已冻结。对于编码前通过规则、牌表和现有代码即可发现的要求，不得在用户完成或 Demo 通过后再作为隐藏条件追加，造成反复返工。
- 用户编码期间，Codex 应围绕已冻结的验收清单进行渐进式教学和检查；发现清单内问题时先指出范围与原因，不直接贴出完整答案。
- Demo 必须一次覆盖已冻结验收清单中的正常路径、拒绝路径及无副作用要求。全部通过后才可在 `PROJECT_STATUS.md` 中将闭环标记为完成。
- 只有获得新的卡牌原文、规则书原页、勘误、官方裁定或真实运行证据时，才允许在冻结后新增或改变要求。此时必须明确说明新证据、影响范围和返工原因，不得把前置审查遗漏归因于用户实现。
- 开始下一阶段前应进行一次阶段边界审查，集中处理结构性欠账；不要在后续单个小任务中零散回补本可提前发现的基础模型问题。

## 规则与卡牌效果依据

- 涉及对局规则、卡牌效果、效果结算、行动合法性、时点、区域、构筑限制或胜负判定的任务，必须先完整读取 `D:\download\战双TCG规则知识库.md`，再检查当前前后端实际实现；不能脱离本项目规则套用其他卡牌游戏的通用设计。
- 规则知识库是根据规则书图片和既有沟通整理的结构化摘要，不是规则书逐字转录件。判断优先级为：卡牌原文高于综合规则；禁止执行高于要求执行；无法执行的部分不执行。
- 遇到知识库未覆盖、措辞歧义、精确时点或争议裁定时，必须明确标记为待确认并回查规则书原页、卡牌原文、勘误或官方裁定，不凭常识补充规则。
- 设计 Java 后端权威规则引擎时，以规则知识库和卡牌原文为依据，以原模拟器中的 `RULES_COVERAGE.md`、`CARD_EFFECT_ARCHITECTURE.md`、`CARD_EFFECT_PROGRESS.md` 及现有 TypeScript 行为模块作为已实现参考；若现有代码与规则依据冲突，应修正代码而不是迁就旧实现。
