# 战双 TCG 联机卡牌模拟器实施计划

更新时间：2026-09-04

## 1. 最终目标

将现有战双卡牌模拟器改造成由 Java 后端权威结算、前后端分离、支持联机对局的完整卡牌模拟器。

最终系统必须做到：

- 双方可以使用合法的 50 张卡组完成整局对战。
- 服务端负责洗切、行动合法性、卡牌效果、规则处理和胜负判定。
- 客户端只提交操作意图，并展示服务端允许该玩家看到的状态。
- 数据库中的卡牌都有明确的效果覆盖状态，不能出现有卡牌文本却静默不执行的情况。
- 遇到规则知识库未覆盖、卡牌措辞歧义或缺少官方裁定的情况，明确标记待确认，不凭其他卡牌游戏经验补规则。

## 3. 固定架构边界

```text
数据库 GameCard
    卡牌定义：卡号、名称、费用、PP、DP、特征、效果原文
             ↓
CardInstance
    本局实体牌：唯一 instanceId + cardNo + 本局状态
             ↓
GameState / PlayerState
    双方区域、回合、阶段、侵蚀、战场、胜负状态
             ↓
CardBehavior
    在真实触发时机依据卡牌原文产生 GameAction
             ↓
ResolutionEngine
    顺序结算动作，需要玩家选择时暂停并等待恢复
             ↓
ActionExecutor
    执行动作，是修改 GameState 的统一入口
```

后续实现遵守以下约束：

- 数据库卡牌定义与本局卡牌实例分离。
- 同一卡号的多张牌使用不同的 `instanceId`。
- 卡牌行为不能直接修改 `GameState`，只能读取受限上下文并产生 `GameAction`。
- `ActionExecutor` 负责执行动作并修改权威状态。
- 新增动作、查询或状态类型时，必须能指出对应的综合规则、牌桌基础流程或实际卡号。
- 不为未经牌表验证的未来需求提前增加类型。
- 服务端决定随机结果；正式对局使用不可由客户端控制的随机源，测试使用可复现的固定随机源。
- 规则动作完成后按规定进入检查时机，不能只完成卡牌移动而遗漏牌组更新、侵蚀、PP 为 0、区域上限或胜负处理。

## 4. 阶段一：完成无特殊效果也能游玩的核心牌桌

### 4.1 目标

即使暂时把所有卡牌视为没有特殊能力，也能由两副合法卡组从开局进行到败北或平局。

### 4.2 固定实现顺序

1. `CardInstance`：本局实体牌及唯一实例标识。
2. `PlayerState`：牌组、手牌、墓地、费用区、信号球区、处理区、战场和侵蚀。
3. `GameState`：双方玩家、回合玩家、回合数、阶段、对局状态和胜负结果。
4. 卡组展开：把保存的卡组明细展开为 50 个本局卡牌实例。
5. 卡组合法性：正好 50 张、同编号最多 4 张、红蓝黄信号球各 4 张，以及数据库卡号有效性。
6. 服务端开局洗切。
7. 双方各抽 4 张起始手牌。
8. 从先攻开始依次换牌，补抽后洗切。
9. 双方设置牌组顶 2 张起始明费。
10. 竖直阶段。
11. 抽牌填充阶段：先攻第一回合抽 1 张，其他正常回合抽 2 张；随后最多设置 1 张明费。
12. 主要阶段：使用角色、道具和普通战术牌，装备，消除信号球，发动基础行动及攻击。
13. 费用支付和属性条件。
14. 攻击宣言、自由时点、阻挡、攻击充能、玩家伤害和角色战斗。
15. 结束阶段、手牌上限、回合结束处理和回合切换。
16. 牌组更新、规则处理、败北与平局。

### 4.2.1 进入第 12 步前的基础模型校正闸门

第 11 步完成后，不直接开始实现主要阶段行动。必须先按以下优先级完成基础模型校正；前一项通过 Demo 后再进入下一项：

1. **操作发起者校验**：所有由玩家主动提交的规则方法必须接收并校验 `playerId`，确认玩家属于本局、当前轮到该玩家且当前阶段/子步骤允许该操作。先修正抽牌填充阶段设置明费接口，再将该约束应用于主要阶段及后续全部玩家指令。
2. **败北后阻断流程推进**：抽牌、牌组更新或其他行动令玩家败北后，当前结算必须停止，不能继续进入设置明费、主要阶段或接受后续普通行动。先建立最小对局状态/结果边界；双方同时败北和平局在第 16 步完成整合。
3. **补齐基础区域**：为 `PlayerState` 增加信号球区和处理区，并提供只读视图及受控移动入口；主要阶段信号球消除、战术牌使用和后续充能必须使用这些正式区域，不能以临时集合代替。
4. **战场 5 卡位模型**：战场必须能够表达 5 个固定卡位、空位和指定卡位放置，并在角色或道具进入战场前完成位置合法性校验；后续装备、升变和协战在此模型上扩展。
5. **卡牌所属玩家建模**：不得依赖解析 `instanceId` 推断归属。必须在 `CardInstance` 或由 `GameState` 管理的权威映射中明确保存所属玩家，并与区域中的操控玩家概念分离，以支持卡牌跨玩家区域、操控变化、协战及离场归属处理。
6. **开局状态一致性加固**：`OpeningMulliganState` 必须与 `GameState` 的双方和先后攻一致，换牌提交只允许发生在 `OPENING`；避免两份独立状态不一致或在开局结束后再次提交。
7. **动态费用上限查询接缝**：基础阶段默认上限为 10，但规则移动不得永久写死该值。保留已建立的 `costZoneLimit` 参数入口；阶段二由统一规则查询器根据持续效果计算实际费用上限、明费上限和暗费上限。实际牌表 `BP03-052` 已确认可将费用区上限变为 11。

校正闸门验收条件：

- 非当前回合玩家不能提交设置明费或主要阶段操作，拒绝时权威状态无变化。
- 任一抽牌流程导致败北后，不再推进普通回合阶段。
- `PlayerState` 能明确表示牌组、手牌、墓地、费用区、信号球区、处理区、侵蚀和 5 个战场卡位。
- 每张本局卡牌都能可靠查询所属玩家，不依赖实例 ID 命名格式。
- 开局状态与顶层对局状态不能出现玩家顺序或阶段不一致。
- 默认费用区上限 10 与效果提高到 11 的底层移动测试均通过。

### 4.3 牌组更新必须完整实现

抽牌、充能或其他逐张处理令牌组为空时：

```text
牌组为空
  ├─ 墓地也为空：该玩家满足败北条件，停止当前结算
  └─ 墓地有牌：墓地全部移入牌组并洗切
                → 侵蚀计数 +1
                → 记录本回合侵蚀发生变化
                → 检查侵蚀是否达到7
                   ├─ 已达到：该玩家败北，停止当前结算
                   └─ 未达到：继续尚未完成的逐张行动
```

### 4.4 阶段验收

- 两副合法卡组可以完成开局。
- 卡牌可以在基础区域之间正确移动。
- 回合四阶段能够完整循环。
- 无特殊效果的角色、装备和战术牌能够按基础规则使用。
- 攻击、阻挡、充能、伤害和角色战斗能够完成。
- 牌组更新不会丢牌、复制牌或跳过侵蚀。
- 能正确判定侵蚀达到 7、牌组与墓地同时为空及双方同时败北。
- 使用固定随机种子的测试能够复现洗牌结果。

## 5. 阶段二：完成通用卡牌效果结算系统

### 5.1 核心组成

- `GameAction`：声明通用规则动作。
- `ActionQueue`：保存待结算动作的先后顺序。
- `ResolutionState`：记录来源卡、操控者、触发时机、当前动作位置和选择绑定。
- `EffectContext`：向卡牌行为提供来源卡、关联卡、受限查询和动作入队能力。
- `ResolutionEngine`：推进结算，遇到玩家选择时暂停，收到合法选择后从原位置继续。
- `ActionExecutor`：执行通用动作并修改 `GameState`。
- 自动能力待机队列与检查时机处理。

### 5.2 触发时机

只迁移实际牌表和现有行为模块已经使用的时机，包括：

- 使用时。
- 出场时。
- 充能时与攻击充能时。
- 攻击时与攻击结束时。
- 阻挡时与其他角色阻挡时。
- 协战时。
- 消除信号球时。
- 回合结束时。
- 起动能力。
- 持续能力及光环。

### 5.3 玩家选择

必须支持：

- 从指定区域按卡名、卡号、类型、特征、费用、PP、横竖状态等条件选择。
- 固定数量、最多数量和允许选择 0 张。
- 同色信号球、费用合计上限等组合约束。
- 多步骤效果中的选择结果绑定。
- 选项选择和可选代价。
- 暂停、校验客户端选择、恢复原结算位置。

### 5.4 阶段验收

从真实牌表选择代表卡，分别覆盖：

- 抽牌。
- 区域移动。
- 选择目标。
- 条件效果。
- 可选效果。
- 多步骤效果。
- 持续效果。
- 玩家选择暂停和恢复。

每张代表卡都需要通过卡牌原文核对、行为测试和实际牌桌触发测试。

## 6. 阶段三：迁移 ST01～ST06 与 BP01 的现有效果

迁移顺序固定为：

```text
ST01 → ST02 → ST03 → ST04 → ST05 → ST06 → BP01
```

每个卡包必须完成：

1. 根据 `card_no` 建立行为注册。
2. 对照数据库效果原文。
3. 对照综合规则。
4. 对照现有 TypeScript 行为模块。
5. Java 单卡行为测试。
6. 实际牌桌触发测试。
7. 同卡号异画或不同印刷共享行为。
8. 卡包注册覆盖审计。
9. 全量回归测试。

一个卡包完成验收后，才进入下一个卡包。

## 7. 阶段四：实现 BP02、BP03 与 PR

迁移顺序固定为：

```text
BP02 → BP03 → PR
```

这些卡不能仅依赖现有前端行为模块，需要逐张依据卡牌原文和综合规则实现。

每张卡最终必须归入以下状态之一：

- `COMPLETE`：效果完整实现并通过测试。
- `NO_GAME_EFFECT`：没有需要引擎执行的游戏效果。
- `PENDING_RULING`：存在无法从当前资料确定的精确时点或争议裁定，并记录缺失依据。

不得使用“检测不到行为就按无效果继续”的静默降级方式。

## 9. 阶段六：前端接入、测试与部署

### 9.1 前端接入

## 10. 当前 Java 实验代码处理原则

当前已有代码暂按以下方式处理：

- 基础方向保留：`GameAction`、`DrawAction`、`RelativePlayer`、`ActionQueue`、`CardInstance`、`CardBehavior`。
- 到阶段二统一定型：`EffectContext`、`GameQuery`。
- 教学临时代码：`DrawOneCardEffect`、`ActionQueueDemo`，在真实卡牌闭环建立后删除。
- `PlayerState` 以阶段一的完整牌桌状态为准，避免只为单个动作反复改变结构。

## 11. 推进与变更规则

- 每次开始开发前，先确认当前所属阶段和本阶段验收条件。
- 一次只推进一个能运行或能验证的闭环。
- 不因单张卡临时推翻已经验证的基础架构。
- 若确需调整架构，必须先指出冲突的规则条款、实际卡牌或运行证据，并记录调整原因及影响范围。
- 每完成一个可运行闭环，更新 `PROJECT_STATUS.md`。
- 长期路线更新本文件；每日事实进度更新 `PROJECT_STATUS.md`。
